# STM — обязательные инструкции для разработчика и агента

Действуют во всём репозитории. Цель — работоспособное совместное прохождение Skyrim, не количество коммитов, проверок или промежуточных подсистем.

## Структура кода

Четыре категории физически разделены: [required/](required/) — утверждённая основа; [important/](important/) — утверждённый незавершённый функционал; [reusable/](reusable/) — полезные наработки; [obsolete/](obsolete/) — отменённое направление. [Карта структуры](docs/REPOSITORY-STRUCTURE.md) объясняет назначение и зависимости, в том числе почему часть obsolete ещё применяется. Это не разрешение удалять или менять поведение. Порядок применения определяет build.yml, не алфавит каталогов. Новые патчи/тесты помещать по назначению, обновлять workflow и журнал; при безопасном выводе старой зависимости отдельно проверить сборку и игровой сценарий. Корневой README — короткая навигация, не спецификация.

## Начало работы, включая новый чат

1. Через подключённый GitHub установить фактический репозиторий Mobelon6/skyrim.together, рабочую ветку development/coop-dialogue-recovery, HEAD, последние изменения и Actions. Не путать с прежним репозиторием с дефисом; main — исторический снимок. Не продолжать только по памяти или старому handoff.
2. Прочитать [COOP-STATUS](docs/COOP-STATUS.md) целиком, последние записи [WORKLOG](docs/WORKLOG.md), обязательные правила в начале [DEVELOPMENT](DEVELOPMENT.md), действующие требования [Coop-Campaign](docs/Coop-Campaign-RU.md) и спецификацию затронутого домена: [HOME-CONCEPT](docs/HOME-CONCEPT-RU.md), [Party-Dialogue](docs/Party-Dialogue-and-Recovery-RU.md). [COOP-HISTORY](docs/COOP-HISTORY.md) — сохранённая история, читать выборочно. [build.yml](.github/workflows/build.yml) — фактический порядок патчей и сборки.
3. Определить ближайший незавершённый функциональный блок по текущему реестру, сверить его реальный код и проверки. После оборванного чата проверить фактическую ветку/CI, не считать план выполненным. Не повторять полный аудит всей истории без необходимости. Контекст прежних чатов не является обязательным для продолжения.
4. Новое явное решение пользователя имеет приоритет: обновить соответствующую спецификацию, текущий реестр и журнал. Старое решение пометить заменённым, не исполнять отменённый подход.

## Действующие принципы

- Skyrim SE 1.6.1170, совместное прохождение двумя игроками с согласованным профилем. Хост хранит единственный авторитет общего мира и журнал кампании; оба клиента имеют личные ESS и проверяемые локальные реплики. Любой участник может инициировать разрешённое действие. Хост, лидер, говорящий, владелец симуляции и владелец личного имущества — разные роли.
- Защита от сетевых хардлоков/софтлоков для квестов, предметов, alias, триггеров, случайных событий, сцен, диалогов, NPC, боя, наград, магии, перемещений, имущества. Один общий исход, личные эффекты каждому имеющему право. Общий предмет/сдача не блокируют второго; при совместном убийстве дракона каждому участвовавшему душа, оба могут изучить слово силы. Не копировать личный баланс душ/навыки хоста и не размножать обычный лут.
- Восстановление после краткого отключения, вылета, загрузки кооп-ESS и рестарта сервера обязательно для каждого механизма. Отличать получение записи, исполнение и сохранение. Не подтверждать новые общие операции без хоста. Длительное самостоятельное соло и автоматическое объединение независимых миров отложены; конфликтующий прогресс не импортировать автоматически.
- Недвижимость физически общая, собственность общая, контейнеры общие по умолчанию с назначением личных. Личные физические инстансы, фантомы, подмена чужого мира, пространственная изоляция поместий и гостевые ESS отменены. Не развивать их заново. Не удалять старые патчи/данные вслепую.
- Сохранить работоспособные механизмы спутников и подтверждённый нелетальный бой. Использовать штатные Skyrim/STR, CampaignJournal/Replication/Identity/Checkpoint, TradeLedger, native ContainerMenu и другие существующие компоненты. Не создавать копию Papyrus VM, вторую БД, генератор игры или универсальный симулятор ради инфраструктуры.

## Рабочий цикл

- Читать реальный затронутый исходник, связанные пути, обе стороны сети, жизненный цикл, версии и API. Для нативного вызова проверить ABI/событие/условия на 1.6.1170; не угадывать. По возможности реконструировать итоговый preimage из pinned upstream и патчей один раз, формировать diff от него, не от случайного vanilla-среза.
- Выполнять крупный ограниченный игровой сценарий до доступного результата. Основной путь, затем реальные риски конкуренции, повтора, обрыва, сохранения/загрузки, потери/дублирования и регрессий. Не откладывать игровую проверку из-за гипотетических случаев. При блокере продолжать независимые задачи.
- Существенные изменения поведения, требований, архитектуры, сложности, безопасности сохранений и компромиссы согласовывать ДО реализации. Объяснять варианты, последствия и рекомендацию. Рутинные технические решения принимать самостоятельно. Не задавать уже отвеченные вопросы. «Продолжай» означает следующий согласованный блок, не разрешение расширить цель.
- Перед записью проверить HEAD/preimage и сохранить чужие изменения, по возможности атомарный коммит с проверкой expected SHA; после записи проверить фактический ref и содержимое. Никаких разрушительных операций без разрешения. При изменении протокола/ESP/ABI учитывать версии обоих клиентов и сервера, совместимость и миграцию.
- Различать изменение исходника, коммит, apply, сценарные тесты, Windows build, сформированный ZIP, доступный архив и реальную игровую приёмку. Не приписывать результат невыполненному этапу. При ошибке читать фактический CI-лог, исправлять причину. Не обходить LICENSING. Не ожидать бесконечно CI: записать run/SHA/стадию, продолжить независимое; проверить при следующем заходе. Сообщать пользователю конкретный результат, ограничения, проверяемые ссылки и следующий шаг.
- Не превращать разработку в бесконечную подготовку. Если подход непропорционально сложен, остановить его расширение, согласовать практический компромисс, не пытаться автоматически создать ещё одну систему. Критерий — работоспособный игровой сценарий.

## Обязательный журнал и состояние — часть готовности задачи

[WORKLOG](docs/WORKLOG.md) — последовательный журнал разработки **и** изменений порядка работы, задач, целей, требований, методов, подхода, принятых/отменённых решений, ограничений, исследований и проверок. Добавлять запись в конец при каждом содержательном изменении, существенном исследовании, принятом решении, смене статуса/приоритета, обнаруженном блокере или результате проверки, включая отказ. Не записывать каждый вызов инструмента или частные рассуждения; фиксировать полезный результат. Ошибочные старые записи не переписывать: новая запись указывает коррекцию. Не публиковать credentials, сейвы, личные данные или проприетарные файлы игры.

[COOP-STATUS](docs/COOP-STATUS.md) — единственная текущая карточка задач с устойчивыми ID, статусом, доказательствами, критерием и следующим шагом. Обновлять при изменении фактического состояния. Не дублировать список задач в журнале; ссылаться на ID. Спецификации — единственный источник нормативного поведения в соответствующем домене, DEVELOPMENT — методика/сборка. Если меняется требование, обновить спецификацию. Если меняется процесс, обновить AGENTS/DEVELOPMENT. Журнал фиксирует почему и когда.

Код и относящиеся записи — в одном коммите, где возможно; завершившийся позднее CI/игровой тест — отдельная запись с точным SHA/run. SHA собственного коммита заранее неизвестен: указать проверенную базу и связанное описание, позднее уточнить ссылку. Документальное решение без кода тоже записывать. В конце значимого рабочего прохода проверить, сможет ли новый чат продолжить только по репозиторию. Отдельный handoff не обязателен и не должен становиться конкурирующим источником истины.
